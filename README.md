# espbpf — верифицируемый eBPF для ESP32

[![ci](https://github.com/drimurak/espbpf/actions/workflows/ci.yml/badge.svg)](https://github.com/drimurak/espbpf/actions/workflows/ci.yml)

Прошивка для ESP32 с датчиком DHT11, реле, светодиодами и круглым дисплеем GC9A01. Логику управления можно менять **на лету по Wi-Fi**. Для этого на обычном C пишется программа, собирается `clang -target bpf` в настоящий байткод eBPF и отправляется на плату. На устройстве программа загружается из ELF, проходит **статическую проверку верификатором** и только потом исполняется интерпретатором.

Это та же идея, что eBPF в ядре Linux, только на микроконтроллере с 520 КБ ОЗУ: чужой код нельзя запустить, пока не доказано, что он безопасен.

```
  ноутбук (Linux)                              ESP32
 ┌──────────────────────┐   Wi-Fi/TCP   ┌───────────────────────────────────────┐
 │ thermostat.c         │               │  ELF-загрузчик (недоверенный ввод)    │
 │   │ clang -target bpf│  LOAD <size>  │        │                              │
 │   ▼                  │ ────────────► │  верификатор ── отказ ──► "ERR pc 12…"│
 │ thermostat.o         │               │        │ ок                           │
 │   │ bpfrun (симуляция│  TRACE        │  интерпретатор ◄── хук "sensor" (2 с) │
 │   ▼  и проверка)     │ ◄──────────── │        │                              │
 │ bpfctl.py load/trace │               │  хелперы: relay_set, led_set, show,   │
 └──────────────────────┘               │  map_get/set, trace, time_ms, random  │
                                        └───────────────────────────────────────┘
```

## Что гарантирует верификатор

Программа, прошедшая проверку:

| Гарантия | Как достигается |
|---|---|
| **завершается** | переходы разрешены только вперёд, граф потока управления ацикличен, число шагов не больше длины программы |
| **не читает мусор** | абстрактная интерпретация: тип каждого регистра (не инициализирован / число / указатель на ctx, стек или rodata) отслеживается по всем путям и сливается в точках соединения |
| **не лезет в чужую память** | разыменовывать можно только указатели, число — никогда; у скаляров и смещений указателей отслеживается диапазон `[lo, hi]`, поэтому `buf[i & 7]` и `if (i < 8) buf[i]` доказываются статически; если диапазон вывести не удалось, границы проверяются в рантайме |
| **зовёт только разрешённое** | номер хелпера и типы аргументов сверяются с окружением хука |
| **не портит контекст** | ctx хука `sensor` только для чтения |

**Защита в глубину:** каждое обращение к памяти в интерпретаторе дополнительно проверяется по границам, а счётчик шагов ограничен длиной программы. Даже ошибка в верификаторе не превратится в порчу памяти или зависание. Если программа всё же упадёт в рантайме, она отключается, а **реле выключается** (fail-safe).

### Чем отличается от верификатора Linux

- **Нет циклов.** В ядре есть bounded loops через перебор состояний, здесь это слишком дорого по памяти. Циклы с константной границей clang разворачивает сам.
- **Диапазоны значений проще, чем в ядре.** Есть `[lo, hi]` для скаляров и смещений указателей, сужение на условных переходах, правила для `&`, `%`, сдвигов и ширины загрузки. Нет `var_off` (трекинга отдельных битов) и 32-битных диапазонов отдельно от 64-битных. Границы клампятся до 32 бит: состояние одной точки ветвления занимает 132 байта, всего не больше 33 КиБ (предел 256 точек).
- **Если диапазон неизвестен, доступ проверяется в рантайме,** а не отвергается. Ядро в таком случае отказывает.
- **`ptr |= scalar` разрешён.** clang генерирует это для `fp_aligned + small`, а ядро такое отвергает (см. `examples/comfort_leds.c`).
- **Нет maps, есть хелперы `map_get`/`map_set`.** Нет вызовов bpf-to-bpf: функции должны быть `static inline`.

Поддерживаются инструкции eBPF v1–v4: ALU/ALU64, JMP/JMP32, знаковые div/mod, movsx, memsx, bswap, gotol, `lddw` со строками из `.rodata` через релокации `R_BPF_64_64`.

## Структура

```
core/       переносимое ядро VM на C11 (тот же код на ESP32 и на Linux)
  vm.c        интерпретатор
  verifier.c  верификатор (2 прохода)
  elf.c       загрузчик ELF + релокации rodata
sdk/        espbpf_prog.h — заголовок для программ (ID хелперов, struct sensor_ctx)
            espbpf_helpers.h — сигнатуры хелперов, общие для прошивки и bpfrun
examples/   thermostat.c, stats.c, comfort_leds.c
tests/      юнит-тесты, программы, которые должны быть отвергнуты, фаззеры
host/       bpfrun — проверка, дизассемблер и симуляция на Linux
tools/      bpfctl.py — загрузка на плату, genfont.py — генератор шрифта
compare/    один и тот же .o через мой верификатор и через верификатор Linux
firmware/   проект ESP-IDF: DHT11, GC9A01, реле, Wi-Fi, TCP-сервер
```

Размер ядра на ESP32: **~12,5 КБ флеша**. На плате загрузка с верификацией занимает около 10 мс, один запуск программы — доли миллисекунды (замеры ниже).

## Подключение

Пины по умолчанию зависят от цели сборки и меняются в `idf.py menuconfig` → `espbpf` → `Pins`.

| Модуль | Контакт | ESP32-S3 | ESP32 (классический) |
|---|---|---|---|
| DHT11 | VCC | 3V3 | 3.3V |
|  | DATA | **4** | **27** |
|  | GND | GND | GND |
| Реле | VCC / GND | 5V / GND | 5V (VIN) / GND |
|  | IN | **5** | **26** |
| Светодиод 0 (красный) | анод через 220–330 Ом | **6** | **25** |
| Светодиод 1 (зелёный) | анод через 220–330 Ом | **7** | **33** |
| Светодиод 2 (жёлтый) | анод через 220–330 Ом | **15** | **32** |
| GC9A01 1.28" | VCC / GND | 3V3 / GND | 3.3V / GND |
|  | SCL | **12** | **18** |
|  | SDA | **11** | **23** |
|  | CS | **10** | **5** |
|  | DC | **9** | **16** |
|  | RST | **14** | **17** |
|  | BLK | 3V3 | 3.3V |

На ESP32-S3 заняты флешем и PSRAM выводы 26–37, а 0, 3, 45, 46 — стартовые, 19 и 20 — USB, 43 и 44 — UART0. Пины по умолчанию их обходят.

Таблица выше — это значения по умолчанию, а не то, что прошито у вас. Прошивка сама сообщает свою распиновку: при старте она пишет её в лог, а команда `pins` отдаёт её по сети. Один и тот же пин у двух модулей и пин, занятый самим чипом, помечаются `!!`:

```
$ ./tools/bpfctl.py 192.168.1.50 pins
DHT11 DATA  GPIO4
relay IN    GPIO5 (active low)
LED 0       GPIO6
...
LCD BLK     not connected
pin map ok
```

Это отвечает на вопрос, с которого начинается половина отладки: программа работает, реле молчит — дело в проводе или в конфиге?

Без резистора светодиоды можно подключать только к пинам из таблицы: для них в прошивке выставлен минимальный ток (`GPIO_DRIVE_CAP_0`).

> ⚠️ **Реле и 220 В:** на макетной плате коммутируйте только низковольтную нагрузку. Сеть 220 В — только в корпусе, с клеммами и изоляцией.

> Большинство синих модулей реле включаются **низким** уровнем (`RELAY_ACTIVE_LOW=y`). Если реле щёлкает наоборот, выключите опцию.

### Отладка на железе

- Первое, что печатает прошивка при старте, — распиновка (та же, что отдаёт `bpfctl pins`). Сверьте её с проводами, прежде чем искать ошибку в коде.
- В логе при старте видно `GPIO[4]| InputEn: 1| OutputEn: 1| OpenDrain: 1| Pullup: 1` — так проверяется настройка пина DHT11.
- Ошибки датчика печатаются с причиной: `sensor silent`, `DATA is stuck LOW`, `late answer`, `checksum mismatch`.
- При старте дисплей показывает цветные полосы; **красная полоса должна быть сверху**. Если нет — смените `LCD MADCTL` (0x08, 0x48, 0x88, 0xC8).

## Сборка и запуск

### 1. Хост: тесты и примеры (Linux)

```bash
sudo apt install clang llvm build-essential
make            # собирает bpfrun, тесты, примеры (clang -target bpf) и прогоняет всё
make fuzz       # фаззеры ELF-загрузчика и верификатора (ASan + UBSan)
ASAN_OPTIONS=detect_leaks=0 ./build/fuzz_verify 3000000 build/corpus_v/*
```

Проверить и прогнать программу без платы:

```bash
./build/bpfrun -t 25,21.5,21,23,24.5,19 build/examples/thermostat.o
./build/bpfrun -d build/examples/thermostat.o      # дизассемблер
./build/bpfrun build/tests/bad/scalar_deref.o      # посмотреть, как отказывает верификатор
```

### 2. Прошивка (ESP-IDF 5.3)

```bash
cd firmware
idf.py set-target esp32
idf.py menuconfig          # espbpf → Wi-Fi SSID/пароль, токен, пины
idf.py build flash monitor
```

После подключения к Wi-Fi дисплей покажет IP-адрес.

### 3. Загрузка программы на плату

```bash
./tools/bpfctl.py 192.168.1.50 load build/examples/thermostat.o
./tools/bpfctl.py 192.168.1.50 status
./tools/bpfctl.py 192.168.1.50 trace       # живой вывод trace()
./tools/bpfctl.py 192.168.1.50 dump        # дизассемблер того, что исполняется на плате
./tools/bpfctl.py 192.168.1.50 pins        # какая распиновка реально прошита
./tools/bpfctl.py 192.168.1.50 unload
```

Последняя загруженная программа сохраняется в NVS и переживает перезагрузку.

## Как писать программы

```c
#include "espbpf_prog.h"

SEC("sensor")                        // вызывается после каждого замера DHT11
int thermostat(struct sensor_ctx *ctx)
{
    if (!(ctx->flags & SENSOR_OK))
        return 0;
    if (ctx->temp_x10 < 220)          // десятые доли градуса
        relay_set(1);
    else if (ctx->temp_x10 > 240)
        relay_set(0);
    show("t=%d.%d", ctx->temp_x10 / 10, ctx->temp_x10 % 10);   // строка на дисплее
    return 0;
}
```

| Хелпер | Что делает |
|---|---|
| `trace(fmt, ...)` | printf-подобный вывод (до 3 аргументов, `%d %u %x %c`) в лог и в `bpfctl trace` |
| `show(fmt, ...)` | то же, но строка на дисплее |
| `relay_set(on)`, `relay_get()` | реле |
| `led_set(i, on)` | светодиоды 0..2 |
| `map_get(k)`, `map_set(k, v)` | 16 ячеек u64, сохраняются между запусками |
| `time_ms()`, `random32()` | время с загрузки, случайное число |

Сборка: `clang -O2 -target bpf -mcpu=v4 -ffreestanding -Isdk -c prog.c -o prog.o`.

## Проверено

- 54 юнит-теста: семантика инструкций (деление на 0, сдвиги, знаковые JMP32, movsx, bswap…), 24 случая отказа верификатора, трекинг диапазонов, рантайм-проверки границ;
- 7 программ на C, которые верификатор обязан отвергнуть: цикл, разыменование числа (попытка писать в регистр GPIO), глобальная переменная, запись в ctx, вызов не-inline функции, неизвестный хелпер, число вместо указателя;
- фаззинг под ASan/UBSan: 3 млн мутированных ELF и 5 млн мутированных программ; около 3% мутантов проходят верификатор и исполняются, ни одной ошибки памяти или неопределённого поведения;
- кросс-компиляция ядра и прошивки под Xtensa (`xtensa-esp32-elf-gcc`, `-Werror=all`) с заголовками ESP-IDF 5.3.1. Сразу нашлась ошибка переносимости: на Xtensa `int32_t` — это `long`.

Всё перечисленное выполняется в CI на каждый push (`.github/workflows/ci.yml`): тесты под ASan/UBSan, 3 млн мутированных ELF и 5 млн мутированных программ, сборка прошивки под `esp32` и `esp32s3`.

### На железе

Проверено на ESP32-S3 DevKitC (8 МБ PSRAM), ESP-IDF 5.3.1: DHT11 читается, GC9A01 рисует, реле щёлкает, светодиоды управляются программой.

| Что измерено | На плате |
|---|---|
| загрузка ELF + верификация (`thermostat.o`, 54 инструкции) | 9,7–11,9 мс |
| один запуск программы (хук `sensor`) | ≈0,7 мс |
| обращений к памяти, доказанных статически | все, ни одной рантайм-проверки |
| падений за сотни запусков | 0 |

Программа сохраняется в NVS: после `reset` плата поднимается с той же логикой, не дожидаясь ноутбука.

Что всплыло только на железе (и починено):

- `gpio_set_direction()` **не** переключает IO MUX на функцию GPIO — это делает только `gpio_config()`. Пока DHT11 и линии RST/BL дисплея настраивались первым способом, датчик молчал, а причина не видна ни в логе, ни в коде.
- Wi-Fi по умолчанию уходит в modem sleep, и плата перестаёт отвечать на ARP: с ноутбука это выглядит как `Destination Host Unreachable`. Лечится `esp_wifi_set_ps(WIFI_PS_NONE)`.
- Таблица хелперов была продублирована в прошивке и в `bpfrun`, и они разошлись: программа, принятая на хосте, отвергалась на плате (`call 8: r4 is not initialised on every path`). Теперь обе стороны собираются из одного X-макроса в `sdk/espbpf_helpers.h`.

Если что-то не заводится: **дисплей зеркальный или повёрнут** → `LCD_MADCTL` (0x08 / 0x48 / 0x88 / 0xC8); **экран чёрный** → BLK и RST; **DHT11 даёт `ESP_ERR_TIMEOUT`** → подтяжка 10 кОм и `bpfctl pins` (чаще всего провод не на том пине).

## Сравнение с верификатором Linux

`compare/run.sh` собирает десяток маленьких программ на C и скармливает каждый `.o` двум верификаторам: моему (`bpfrun`) и тому, что в работающем ядре (`compare/kverify.c` — свой разбор ELF и `bpf(BPF_PROG_LOAD)` с типом `socket_filter`). Нужны clang с целью bpf и **root**: загрузка BPF-программы требует `CAP_BPF`, а непривилегированный `bpf()` на большинстве дистрибутивов выключен (`kernel.unprivileged_bpf_disabled=2`). Скрипт сам поднимает права через sudo; без прав колонка ядра остаётся пустой, и это честно печатается как «вердикта нет», а не как отказ.

Из десяти случаев вердикты сходятся в шести (проверено на ядрах 6.17 и 6.18 — совпало построчно). Расхождения:

| Случай | Linux 6.18 | espbpf |
|---|---|---|
| цикл с границей из ctx | принят (ограниченные циклы) | отвергнут: back-edge |
| `buf[i & 7]` → `r2 \|= r1` | отвергнут: `bitwise operator \|= on pointer prohibited` | принят, доступ доказан статически |
| `buf[i]` без границы | отвергнут: `unbounded variable-offset` | принят, границы проверяются в рантайме |
| 4098 инструкций | принят (предел 1 000 000) | отвергнут: предел 1024 |

Самое поучительное — первые две строки вместе: `buf[i & 7]` и `if (i < 8) buf[i]` делают одно и то же, но clang выражает первое через `|=` над указателем, и ядро отказывает. Вердикт зависит не только от того, безопасна ли программа, но и от того, какой идиомой её выразил компилятор.

## Идеи для развития

1. **Сравнение с верификатором Linux:** прогон тех же `.o` через `bpftool prog load` с разбором, где и почему вердикты расходятся.
2. **Ограниченные циклы** (`bpf_loop` как хелпер с колбэком).
3. **Настоящие maps** через секцию `.maps` и `BPF_PSEUDO_MAP_FD`, совместимые с libbpf.
4. **JIT в Xtensa или RISC-V** и замер ускорения против интерпретатора.
5. **Больше хуков:** `timer` (каждые 100 мс), `gpio` (прерывание по кнопке), writable ctx.
6. **DHT11 через RMT.** Аппаратная фиксация фронтов вместо bit-banging в критической секции.
